Development log · Beta 1.1

What we're building

SD Sourcing Agent is an experiment in making AI judgments about people reliable enough for recruiting: every score has to point at evidence, and every claim a model makes about a candidate has to be checkable against a profile.

Started 2026-08-30 · Last updated 2026-10-29

The problem

A language model asked to “find me candidates for this job” returns confident, unverifiable answers. Recruiters need the opposite: a short list they can calibrate with a client, a score that can be audited, and numbers they can trust. The work below is the trial-and-error of getting from a model that sounds right to a system that can show why.

Development log

Newest first. Dates are when the work landed.

  1. 2026-09-30

    Checking the model's ratings against the evidence

    Goal. The model rates each candidate against the role's must-haves, but nothing independent checked those ratings. We added a second, separate model that reads each returned profile and judges every requirement as supported, contradicted, or not stated.

    What didn't work. The first comparison flagged almost every candidate as a disagreement (four of six in a test), which is noise, not signal.

    What we changed. Separated a real conflict (the model rates someone highly while the profile contradicts a requirement) from an unverified rating (the profile simply doesn't say). Missing evidence is not treated as a contradiction. 60 automated tests cover the logic.

  2. 2026-09-24 → 09-25

    Talent Mapping: exact headcounts instead of samples

    Problem. The first version sampled a page of people and extrapolated. The data source hides most employer details and surnames, so a sample could be badly off.

    What we found. The source reports a total count independent of the page returned, so a headcount grid (company × location × title) can use exact counts at no per-lookup cost. A company-name filter also matches loosely (one name resolved to several unrelated companies), so each row now shows which companies it was actually built from.

    Still imperfect. Two data sources disagree on the same market (see open questions).

  3. 2026-09-02 → 09-05

    Submission Builder, saved history, and exports

    Added a tool that turns interview notes, a resume and a job description into a structured candidate submission, with server-side saved history for both slates and submissions, plus CSV and PDF export. Long model outputs were being cut off mid-structure or exceeding schema limits, so we raised the output ceiling and made the system trim over-long lists instead of failing the whole run.

  4. 2026-08-30 → 09-02

    From a scoring script to a job-description-to-slate product

    Began with a deterministic rubric that scores a slate of candidates on weighted dimensions, then built a web product around it: paste a job description, get a banded, scored slate with evidence for each rating. Along the way we had to fit a long, tool-using search run inside the hosting platform's time limit, diagnose runs that came back empty, cache the static part of the prompt, report per-run cost, and move to a more cost-effective model. A recalibration pass lets recruiter feedback on one slate steer the next search, and recruiters can state their own must-haves and nice-to-haves.

Open questions

What we don't yet know how to do well.

How much should an independent check be trusted?

We don't yet know the right confidence threshold for accepting the second model's verdict, or whether individual requirements should be weighted (two candidates with different strengths currently score the same coverage). The real-run behaviour of the check is still being measured.

Why do two data sources disagree on the same market?

For one test query, one source counted 622 matching people and another listed 397. We don't yet know how much is differing definitions of “role” and location versus genuine coverage gaps.

How deep can a profile screen go?

Structured profile data carries titles, skills and dates but not what someone actually did. We're working out which judgments can be made reliably from that data and which need a human conversation.

This is a living, informal log of an experimental product. It describes our work in progress and is not a guarantee of results.
